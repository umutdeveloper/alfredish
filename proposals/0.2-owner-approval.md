# Proposal: owner approval (Alfredish v0.2)

> Status: **draft — waiting for the owner.** Nothing here is in SPEC.md yet. When approved, the parts move into
> SPEC.md, then tests, then code (CLAUDE.md workflow). Tests already exist for every hole named here:
> `test/attacks.test.ts` (17 known holes, 4 caught mistakes, 1 control).

## 1. Problem

Alfredish checks the **shape** of a memory (types, links, the past, generated views) and the **world** (probes,
expiry). It does not check **who wrote it**. Every "the owner approved this" in a memory is a string an agent can
type: `review({ by: "owner", at })`, `confirm({ by: "owner", at })`, `local(path, { confirmedBy: "owner", at })`.
So an agent can approve its own work, and the attack tests show it does pass: a forged local path, a self-renewed
decision, a weakened rule, a postponed promise, a deleted rule, a back-dated decision — all green.

## 2. Threat model

Two kinds of agent, two guarantees:

| Agent | Example | Guarantee |
|---|---|---|
| **Careless** — makes mistakes, means well | writes a path in a title, forgets a file in the index | The normal gate (`alfred check`, the hook) catches it **and says what the right form is**. |
| **Cheating to get green** — weak agents do this: change the test, not the work | renews its own approval, edits its copy of Alfredish, commits with `--no-verify` | It may fool its own gate, but **nothing it writes counts as approved** until the owner approves it, with a tool and a key the agent cannot change or use. |

Out of scope: an agent with the owner's physical presence (it cannot touch the fingerprint sensor), and the owner
approving something without reading it.

## 3. Principle

> **The agent may write anything. Nothing it writes looks approved until the owner approves exactly that content.**

"Exactly that content": an approval covers one definition's content hash. Change one character and the approval no
longer matches.

## 4. Prerequisite: tests become data

Today a probe is a closure. `snapshot.ts` drops functions, so a probe's hash is only its description: an agent can
empty `page(url).contains("$290")` and keep the description; the hash does not move. Signing that is meaningless.

- A probe becomes data: `{ probe: "page.contains", url, text }`, `{ probe: "cmd", command, args, expect }`, etc.
  The code that runs each probe kind lives in Alfredish, not in the memory.
- `probe(describe, fn)` is removed from what a memory may use. A new probe kind is added to Alfredish (with tests),
  never written inline in a memory.
- `cmd("…", "true", [])` stays possible, but it is now visible content: the owner sees `runs: true` in the approval
  list (§6). Closes hole 05; makes hole 06 visible.

## 5. Approval records

- **What is approved:** the snapshot (already computed for K5 and `alfred diff`): every definition's id and content
  hash, probes now included (§4).
- **The approved state:** `approvals/` in the memory holds one record per approval round:
  `{ at, base: <previous record>, approved: {id: hash}, removed: [id], rejected: {id: note}, corrections: {id: note} }`
  plus a detached signature of the record. Records chain (`base`), so history cannot be rewritten without breaking
  the chain.
- **The signature:** a standard SSH signature (`ssh-keygen -Y sign`, namespace `alfredish`). **Verifying** needs only
  the owner's public key and `ssh-keygen`, which ships with macOS, Linux and Windows: any agent on any machine can
  check approvals, and no agent ever needs to sign. No new npm dependency.
- **The key is the owner's choice, not the language's.** Alfredish requires only "an SSH signing key the agent
  cannot use on its own". Where it lives is the owner's setup, recorded in the owner's memory, not in Alfredish:
  a Secure Enclave key that asks for Touch ID on every use (e.g. the Secretive app on macOS), a hardware key
  (YubiKey, any OS), Windows Hello, or — weakest — a passphrase-protected key file.
- **The anchor (who the owner is):** the owner's public key in a file the agent cannot write — outside the memory,
  writable only by an administrator, installed once (`sudo` / admin rights). Default place per OS
  (`/etc/alfredish/owner.pub` on macOS/Linux, `%ProgramData%\alfredish\owner.pub` on Windows), overridable.
  A public key inside the repository would not do: the agent could add its own. (GitHub's published keys are not
  used either: the agent's `gh` login might be able to add one.)
- **Only listed keys sign:** the anchor is a list of the owner's public keys (one per device or hardware key).
  `alfred approve` signs only with a key on that list and never falls back to another key it finds (e.g. a plain
  file in `~/.ssh`, which needs no fingerprint and which an agent can read). On a machine with no listed key, the
  list is shown, nothing is recorded, and the changes stay unapproved: "no owner key on this machine — nothing
  recorded". Adding a key to the list is an administrator change on that machine.
- **The owner's habit is part of the design:** any program can ask the key to sign, so an agent can trigger a
  fingerprint prompt. The owner gives the fingerprint **only while running `alfred approve` themselves**. With
  Secretive the prompt names the asking app ("sign a request from “Claude” using secret “alfred-owner”"): a prompt
  naming the agent's app instead of the owner's terminal is refused. The prompt text is the key store's, not ours,
  so no code of ours can be shown in it.

## 6. Approving: `alfred approve` (run by the owner, in their own terminal)

The approve tool is installed root-owned next to the anchor, so editing the memory's `vendor/` copy changes nothing
about it. It compares the memory with the last signed record and lists every difference, grouped:

```
5 changes since your last approval (2026-10-03):
  + realtyme.workspace        new asset · local /Users/…/rt · test: folder has git/ and worktrees/
                              why: "Umut confirmed the folder in chat"
  ~ rule.ada.budgetCap        text: "at most 15,000 TL" → "at most 150,000 TL"
                              why: "raised the budget"
  - rule.advice.noInvestment  removed
                              why: (none given)              ← red: a change needs a reason
[a]pprove  [c]orrect…  [r]eject  [enter] skip
```

- **Two groups, decided structurally (by type and verify kind, never by text):**
  1. **Your calls** — shown first, in full: decisions, rules, promises, goals, ideas, anything verified by
     `review`/`confirm`, everything tested by `cmd`, every `local()` path, every removal. Only the owner can know
     whether these are right (for `cmd`: whether the command tests the right thing; the full command is shown).
  2. **Machine-checked** — shown after, one line each, approvable together with one key: facts, assets, accounts
     and claims verified by a probe of a built-in test kind (not `cmd`). The probe already says whether they are true in the world; what is left for the
     owner is "is this the right test?", so the line shows the test itself (e.g. `test: page … contains "$290"`,
     `test: runs true`). Both groups are covered by the same signature.
- **`why`** comes from the session: every change carries a one-line reason in the session definition
  (`changes: { id: reason }`). A change without a reason is red — structural, no text search.
- **Approve:** the content hash is recorded as approved.
- **Correct:** the owner writes a short note ("keep 15,000, only make the wording clearer"). The note is recorded and
  becomes a task for the agent. The agent's new version comes back in the next list — **it is approved again**,
  because the agent wrote it — shown as the difference between its first and second try, with the note above it.
- **Reject:** recorded with an optional note. The definition must return to its last approved hash; the check is red
  until it does (the agent restores it, e.g. from git; the check verifies the hash, not the agent's word).
- **Skip:** nothing recorded; the change stays **unapproved** and comes back next time.
- One fingerprint signs the whole round.

## 7. What "unapproved" does

- A definition whose current hash is not the approved one is **unapproved**. So is everything that rests on it (K3).
- Unapproved is not red: it does not stop a commit, so work never has to stop. It is shown at the top of `NOW.md`
  (count + ids), and `alfred get` says "unapproved — do not rely on this" (like red today).
- Red stays red for what is wrong (failed probe, expired review, rejected-but-not-restored, change without a reason).

## 8. Rules that become structural with an approved state

- **K5 against the last signed record, not `HEAD`:** a past rewrite committed with `--no-verify` is still caught.
  Closes hole 17.
- **Deletion:** an approved id that is gone is a change (`-` in the list) and needs approval. Closes hole 08.
- **Birth:** a definition that is not in the last signed record must have as `origin` a session that is not in it
  either (the session being worked in). Closes hole 12 (back-dating), with the message
  "new definition born in an approved session: use today's session".
- **`review`, `confirm`, `local()` lose their `by`/`confirmedBy` strings:** the date of the owner's approval is the
  date of the signed record that approved that content. Closes holes 03, 04 (an agent can still write a new date, but
  that is a change the owner sees).

## 9. Messages that say the right form

Every red or unapproved line names the fix, e.g.

- `rule.x — changed without a reason: add "rule.x": "<why>" to the session's changes`
- `work.y — new, born in s.2026-10-01 (approved): use today's session as origin`
- `work.z — rejected on 2026-10-04 ("keep 15,000"): restore the approved version (git show <commit>:<file>)`

| Hole (attack test) | After this proposal |
|---|---|

| 05 always-passing probe closure | **Impossible** (§4) |
| 06 `true` command | **Visible** in the list (§4) |
| 08 deleted rule · 12 back-dating · 17 `--no-verify` past rewrite | **Red / unapproved**, structurally (§8) |
| 16 edited vendor copy | Fools only the agent's own gate; **the owner's approve tool is untouched** |

## 11. Decisions for the owner

1. **The owner's key (owner setup, not language):** Secretive on this Mac, one key that asks for the fingerprint
   on every use. Decided 2026-10-03.
2. **Anchor (decided 2026-10-03: yes):** one `sudo` install of the public key and the approve tool, root-owned. Recommendation: yes; without
   it the agent can replace "who the owner is".
3. **Principle 3 (decided 2026-10-03: yes, hints only):** keep it for rules; allow text checks only as **hints that never decide**
   (e.g. "looks like a local path → use `local()`"). Recommendation: yes; the decision stays with the approval.

## 12. Order of work (each step: spec → failing test → code)

1. Probes as data (§4).
2. Approval records, verify with `ssh-keygen`, the unapproved status (§5, §7).
3. `alfred approve` with the list, correct/reject/skip (§6).
4. K5 against the signed record, deletion, birth, `by` strings removed (§8).
5. Fix messages (§9). Then the two small proposals of §10.

Spike on the owner's setup (Secretive 4.0.0, macOS 26.6, 2026-10-03) — done:
- `ssh-keygen -Y sign` through Secretive's agent socket works; `ssh-keygen -Y verify` accepts it with only the public
  key; a message changed by one character is rejected.
- Every signature asks for the fingerprint separately (two signatures 2 s apart: two prompts, per the agent's log).
- The prompt names the asking app; no private key file exists on disk.
- The very first request right after setup failed ("communication with agent failed"): the agent restarted once.
  It did not happen again.

Alfredish's own tests use a plain throwaway key: the language is tested without any particular key store.

## 13. Test kinds to add (so `cmd` stays rare)

A real memory's 24 `cmd` tests, grouped by what they check:

| Check | Uses | Becomes |
|---|---|---|
| a GitHub repository exists / is gone | 10 | `github(owner/name).exists()` / `.absent()` |
| a domain's registration ends on or after a date (today: `whois` + a date regex) | 4 | `domain(name).expiresOnOrAfter(date)` |
| a DNS record has / lacks a value, optionally at one name server | 4 | `dns(name, type, { server? }).contains(value)` / `.lacks(value)` |
| a git repository has no remote | 2 | `git(repo).noRemote()` |
| a local folder has given sub-folders | 1 | stays `cmd` (`file.exists` checks one path; a weaker test is not a fix) |
| text in memory names a machine path | 1 | stays the memory's own self-testing check; Alfredish adds a hint (principle 3 decision) |
| anything else (current user, one API answer, commit subjects are ASCII) | 3 | stays `cmd` |

The date regexes show why: a pattern meant as "2027-07-06 or later" also accepts 2027-07-01…05. A test kind that
compares dates as dates cannot make that mistake.
